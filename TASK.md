# Ticks to Bars Converter
Утиліта для перетворення тіків в бари.

## Завдання
- Створити утиліту для перетворення тіків в бари.
- Вхідні параметри можуть бути введені через файл конфігурації або через аргументи командного рядка (вищий пріоритет).
- Документація повинна бути написана англійською мовою.
- Код повинен бути структурований, добре організований і покритий тестами.
- Утиліта повинна бути скомпільована під Linux, MacOS та Windows платформи.

## Інстументи
- Go 1.xx (імплементація)
- Makefile (збірка)
- Toml (конфігурація)

## Обмеження
- Утиліта працює з файлами в форматі CSV.
- Утиліта працює з таймфреймами від 1 секунди.

## Конфігурація
Файл конфігурації `config.toml` повинен мати наступний вигляд:
```toml
input_dir = "ticks" # директорія для файлів тіків, --input-dir="ticks"
output_dir = "bars" # директорія для збереження барів, --output-dir="bars"

symbols = "EURUSD,GBPUSD,XAUUSD,NAS100" # символи, --symbols="EURUSD,GBPUSD,XAUUSD,NAS100"
available_timeframes = "1m,2m,3m,5m,10m,15m,30m,1h,2h,4h,6h,8h,12h,D,W,M,Y" # доступні таймфрейми, статична конфігурація
timeframes = "1m,15m,1h" # таймфрейми, --timeframes="1m,15m,1h"
include_header = false # включати заголовок в файли барів, --include-header=false
ticks_timestamp_layout = "2006.01.02 15:04:05.000" # формат timestamp у файлах тіків, --ticks-timestamp-layout="2006.01.02 15:04:05.000"
bars_timestamp_layout = "2006-01-02 15:04:05" # формат timestamp у файлах барів, --bars-timestamp-layout="2006-01-02 15:04:05"

force = false # перезаписати вже існуючі бари, --force=false
write_batch_size = 1000 # розмір батча для запису даних в файл, --write-batch-size=1000
```

## Команди
Кожна команда може приймати додаткові параметри.
Команда може бути тільки одна, інакше утиліта завершує роботу з помилкою.
Відсутність команди показує довідку і завершує роботу.

### Команда: help
Показує довідку і завершує роботу.

Виконання:
```bash
ticks2bars help
```

### Команда: version
Показує версію і завершує роботу.

Виконання:
```bash
ticks2bars version
```

### Команда: convert
Перетворює тіки в бари.

Виконання:
```bash
ticks2bars convert [options]
```

### Тип файлів
Файли тіків мають таку конвенцію імен: `<SYMBOL>_ticks.csv` (наприклад: EURUSD_ticks.csv).
- `SYMBOL` - символ

Розмір файлу тіків може перевищувати 20 Гб, тому утиліта повинна вміти працювати з великими файлами.

Файли тіків мають формат:
```csv
<TIMESTAMP>,<BID>,<ASK>
```
- `TIMESTAMP` - timestamp
- `BID` - ціна Bid
- `ASK` - ціна Ask

Наприклад:
```csv
timestamp,bid,ask
2003.05.05 03:00:05.536,1.12161,1.12177
2003.05.05 03:00:06.561,1.12166,1.12182
2003.05.05 03:00:14.085,1.12163,1.12183
2003.05.05 03:00:14.420,1.12173,1.12183
2003.05.05 03:00:15.110,1.12170,1.12190
```

Файли барів мають таку конвенцію імен: `<SYMBOL>_<TIMEFRAME>.csv` (наприклад: EURUSD_1m.csv).
- `SYMBOL` - символ
- `TIMEFRAME` - таймфрейм

Файли барів мають формат:
```csv
<TIMESTAMP>,<OPEN>,<HIGH>,<LOW>,<CLOSE>
```
- `TIMESTAMP` - timestamp
- `OPEN` - ціна відкриття
- `HIGH` - максимальна ціна
- `LOW` - мінімальна ціна
- `CLOSE` - ціна закриття

Наприклад:
```csv
timestamp,open,high,low,close
2003-05-05 03:00:00,1.12169,1.12316,1.12161,1.12266
2003-05-05 04:00:00,1.12237,1.12268,1.12109,1.12145
2003-05-05 05:00:00,1.12151,1.12218,1.12098,1.12160
2003-05-05 06:00:00,1.12130,1.12186,1.12059,1.12172
2003-05-05 07:00:00,1.12103,1.12180,1.12081,1.12124
```

Примітки:
- Тіки не містять інформацію про обсяг.
- Тіки відсортовані за зростанням timestamp.
- Хедер в файлі тіків може бути відсутній. Він завжди пропускається, якщо присутній.
- timestamp - це час брокера (без прив'язки до часового поясу чи DST).
- timestamp для тіків і барів описується в конфігурації.

### Конвенції
Припускається, що дані у файлах тіків являються валідними.
Ціни в файлах тіків мають однакову кількість знаків після крапки.

Ціна OHLC має бути розрахована на основі цін Bid і Ask:
- `OPEN = (Bid + Ask) / 2` першого тіка
- `HIGH = MAX(mid)`, де `mid = (Bid + Ask) / 2` від максимальної ціни по всіх тіках бару
- `LOW = MIN(mid)`, де `mid = (Bid + Ask) / 2` від мінімальної ціни по всіх тіках бару
- `CLOSE = (Bid + Ask) / 2` останнього тіка

Ціни OHLC тримаються як масштабовані `int64` (`price × 10^digits`), де `digits` кількість знаків після крапки. Кількість знаків після крапки в ціні барів (`digits`) має бути такою ж, як і в цінах з першого цінового рядка. Фінальне значення ціни OHLC розраховується як `price / 10^digits` з округленням `away-from-zero` як звичне для фінансових даних.

Ціни виводяться завжди з рівно `digits` знаками після крапки, з кінцевими нулями.

timestamp бару це початок інтервалу, обчислений як `floor(ts першого тіка)` за правилами вирівнювання.

Маркер таймфрейму являє собою один або два останні символи у його назві.
Існує декілька варіантів маркерів таймфреймів:
- `s` - секунда (межі: 1-59, бо 60 секунд це хвилина)
- `m` - хвилина (межі: 1-59, бо 60 хвилин це година)
- `h` - година (межі: 1-23, бо 24 години це день)
- `D` - день (межі: 1-27, бо 28-31 день це місяць)
- `W` - тиждень (межі: 1-3, бо 4 тижні це місяць)
- `MN` - місяць (межі: 1-11, бо 12 місяців це рік)
- `Y` - рік (межі: 1-9999, бо 10000 рік це епоха)

Регістр має значення. Утиліта валідує маркер таймфрейму і завершує роботу з помилкою, якщо він не відповідає вимогам.
Число перед маркером обов'язкове, інакше утиліта завершує роботу з помилкою.

Для таймфреймів `D`, `W`, `MN` і `Y` початок відліку визначається окремо:
- `D` - початок дня - 00:00:00.000
- `W` - початок тижня - понеділок
- `MN` - початок місяця - 1 число
- `Y` - початок року - 1 січня

Інтервали рахуються від початку батьківської одиниці (доба для `s`/`m`/`h`, тобто `00:00:00.000`) з допустимим коротшим останнім інтервалом (якщо не вистачило тіків для повного бару).

### Архітектура
Програма складається з декількох основних компонентів:
- Головний потік програми (main)
- Робочі потоки (workers):
  - reader - потік для читання даних (reader)
  - handler - потік для обробки даних (handler)
  - writer - потік для запису даних (writer)

#### Фаза: Валідація вхідних параметрів та конфігурації
Спочатку перевіряється валідність вхідних параметрів та конфігурації головним потоком.
Якщо є невідповідність, то утиліта завершує роботу і виводить повідомлення про помилку.

Перевіряється, чи існує директорія `output_dir` і чи є вона доступною для запису.
Якщо директорія не існує, то головний потік створює її.
Якщо директорія існує, але не є доступною для запису, то утиліта виводить повідомлення про помилку і завершує роботу.

#### Фаза: Створення списку комбінацій символів і таймфреймів для перетворення
Головний потік створює список комбінацій символів і таймфреймів для перетворення.

Наприклад, для `symbols = "EURUSD,GBPUSD"` і `timeframes = "15m,1h"` буде створено список комбінацій:
```json
[
    {
        "symbol": "EURUSD",
        "timeframes": ["15m", "1h"]
    },
    {
        "symbol": "GBPUSD",
        "timeframes": ["15m", "1h"]
    }
]
```

Вимоги:
- Список має бути відсортований за символом (алфавітний порядок).
- Кожен елемент списку має бути унікальним для символу.
- Список таймфреймів для кожного символу має бути відсортований в порядку зростання.

#### Фаза: Перевірка файлів тіків
Для кожного символу зі списку перевіряється, чи існує файл тіків.
Якщо файлу тіків для потрібного символу не існує або він не читається, то утиліта виводить повідомлення про помилку і завершує роботу.

#### Фаза: Перевірка файлів барів
Перед початком роботи отримується інформація про вже існуючі бари в директорії `output_dir` для потрібного символу і таймфрейму.
Якщо файл існує і `force = false`, то утиліта виводить ім'я файлу і повідомлення про те, що файл вже існує. При цьому таймфрейм видаляється зі списку для даного символу.
Якщо файл існує і `force = true`, то утиліта перезапише файл.

#### Фаза: Перетворення даних в бари
Утиліта обробляє символ за символом послідовно, щоб обмежити використання пам'яті.

Для кожного символу головний потік створює:
- робочий потік `reader` для однопотокового читання даних
- робочий потік `writer` для майбутнього запису даних
- робочі потоки `handlers` для обробки даних

Робочий потік `reader` створює декілька каналів `input_channel` для обробки даних для кожного таймфрейму.
Робочий потік `reader` читає дані з файлу і відправляє їх в кожен канал `input_channel` для обробки, а робочі потоки `handlers` отримують дані і обробляють їх.

Маркером формування бару є межа інтервалу таймфрейму або новий тік наступного бару.
Як тільки `reader` закінчить читання даних, він закриває всі канали (`input_channel`).

Кількість робочих потоків `handlers` визначається кількістю таймфреймів для символу і відповідно кількістю каналів `input_channel`.

Кожен робочий потік `handler` відповідає за обробку даних для комбінації одного символу і одного таймфрейму. Він створює свій канал `output_channel` для запису даних.
Він читає дані з каналу (`input_channel`), накопичує їх в буфер, а потім перетворює їх в бари і відправляє в канал (`output_channel`), якщо бар був сформований.
Якщо дані закінчились, але бар не був сформований, то робочий потік `handler` формує бар з наявними даними в буфері. Після цього він закриває канал `output_channel`.

Робочий потік `writer` отримує дані з усіх каналів (`output_channel`) і зберігає бари у відповідний файл символу і таймфрейму.
Запис даних здійснюється батчем (batch), розмір якого визначається конфігурацією (`write_batch_size`) - або залишок даних в каналі.

Коли всі бари для символу були збережені для всіх його таймфреймів, головний потік очікує завершення всіх робочих потоків (`sync.WaitGroup`).
Перехід до наступного символу можливий лише після того, як writer зробив фінальний flush і закрив усі файли.

Для наступного символу всі дії повторюються знову.
